# Розділ 4. Архітектура та реалізація бібліотеки Loki23

У даному розділі детально розглядається архітектура, структурна організація та програмна реалізація оновленої бібліотеки Loki23. Основною метою розробки було глибоке переосмислення та перенесення класичних ідей, архітектурних парадигм та патернів проектування, закладених видатним інженером Андрієм Александреску у його початковій бібліотеці Loki, на сучасну кодову базу з використанням передових стандартів C++20 та C++23. Цей процес вимагав не просто механічного переписування існуючого коду, а ретельного аналізу кожного архітектурного рішення крізь призму еволюції мови програмування C++ за останні двадцять років.

Оригінальна бібліотека Loki, докладно описана у фундаментальній та культовій книзі "Modern C++ Design: Generic Programming and Design Patterns Applied" (2001 рік), здійснила справжню революцію у світі програмування на C++. У той час, коли більшість розробників лише починала освоювати базові можливості об'єктно-орієнтованого програмування, Александреску продемонстрував безмежні, майже магічні можливості метапрограмування на основі шаблонів (Template Metaprogramming). Він вперше системно представив концепцію дизайну на основі політик (Policy-Based Design), винайшов списки типів (TypeLists), які дозволяли маніпулювати типами на етапі компіляції так само легко, як звичайними даними під час виконання програми, та запропонував узагальнені, високонастроювані реалізації класичних патернів проектування "Банди Чотирьох" (GoF), таких як Singleton, Smart Pointers, Abstract Factory, Visitor та багатьох інших. 

Проте, варто зазначити, що оскільки бібліотека Loki створювалася для стандарту C++98, її внутрішня реалізація неминуче містила значну кількість архітектурних компромісів, обхідних шляхів (workarounds), надзвичайно складних рекурсивних шаблонних конструкцій та небезпечних макросів. Це було зумовлено серйозними обмеженнями тогочасних компіляторів та самої мови, яка ще не мала вбудованих механізмів для вирішення багатьох завдань узагальненого програмування.

З виходом нових, епохальних стандартів мови, починаючи з C++11 і закінчуючи C++14, C++17, C++20 та останнім C++23, мова C++ зазнала кардинальних, тектонічних змін. З'явилися варіативні шаблони (Variadic Templates), які назавжди змінили підхід до роботи зі списками типів; семантика переміщення (Move Semantics), що радикально підвищила продуктивність програм за рахунок уникнення зайвих копіювань; згортки шаблонів (Fold Expressions), які дозволили писати лаконічний код замість громіздкої рекурсії; строга та передбачувана модель пам'яті для багатопотоковості (Memory Model); концепції (Concepts), що формалізували вимоги до шаблонних параметрів, та модулі (Modules), які кардинально змінили систему включення файлів і пришвидшили компіляцію. 

Впровадження всіх цих новітніх мовних конструкцій дозволило не лише значно підвищити продуктивність коду та абсолютну безпеку типів, а й суттєво спростити внутрішню реалізацію найскладніших метапрограмних механізмів, зробивши їх зрозумілими для ширшого кола розробників. Бібліотека Loki23 є прямим результатом цього масштабного переосмислення: вона дбайливо зберігає концептуальну красу, гнучкість та елегантність Policy-Based Design, але повністю переписує її фундамент інструментами сучасного C++, перетворюючись з геніального академічного експерименту на надзвичайно надійний, швидкий та безпечний інструмент для розробки сучасних високонавантажених та високопродуктивних програмних систем.

## 4.1. Переосмислення ієрархії політик за допомогою обмежень (Constraints) та концептів (Concepts)

Дизайн на основі політик (Policy-Based Design) є ключовою, фундаментальною архітектурною парадигмою класичної бібліотеки Loki. Суть цього підходу полягає у тому, що він дозволяє розробникам створювати надзвичайно гнучкі, потужні та легко розширювані класи шляхом комбінування простих, сфокусованих на одній задачі та ортогональних (незалежних одна від одної) компонентів — так званих політик. Клас-господар (Host Class, наприклад, розумний вказівник або синглтон) успадковує або агрегує ці політики як базові класи або члени даних, отримуючи таким чином потрібний набір поведінок, який конфігурується розробником виключно на етапі компіляції. Це усуває необхідність у використанні віртуальних функцій та пов'язаних з ними накладних витрат часу виконання (runtime overhead), зберігаючи при цьому поліморфну поведінку.

Однак у стандартах C++ (аж до появи C++20) існувала серйозна проблема: перевірка того, чи дійсно переданий тип політики задовольняє всім необхідним синтаксичним та семантичним вимогам (наприклад, чи має він потрібні методи з правильними сигнатурами, чи підтримує певні оператори), відбувалася лише на етапі інстанціювання тіла самого шаблону. Цей підхід у спільноті розробників часто називали неявною типізацією або «качиною типізацією» на рівні компіляції (compile-time duck typing). 

Якщо користувач через помилку передавав некоректний тип, який не мав потрібного методу, компілятор покірно намагався розгорнути шаблон, заглиблюючись у його внутрішні виклики та рекурсії. Зрештою, натрапивши на відсутній метод або несумісний тип десь глибоко в надрах бібліотеки, відбувалася фатальна помилка компіляції. Як наслідок, компілятор видавав величезні, абсолютно незрозумілі та лякаючі повідомлення про помилки (так звані template error cascades або template error messages), які часто могли сягати сотень, а то й тисяч рядків нечитабельного тексту для однієї-єдиної дрібної помилки користувача. Це робило використання шаблонних бібліотек справжнім жахом для новачків.

У минулому (в епоху C++11/14/17) цю проблему намагалися частково вирішувати за допомогою складної і заплутаної ідіоми SFINAE (Substitution Failure Is Not An Error) або використання стандартних метафункцій типу `std::enable_if`. Проте SFINAE завжди залишалося своєрідною "милицею" — синтаксично перевантаженим, важким для розуміння та підтримки механізмом, який суттєво погіршував читабельність вихідного коду бібліотеки та значно збільшував час компіляції через необхідність перевірки багатьох хибних гілок перевантаження.

У бібліотеці Loki23 цей підхід був фундаментально, докорінно переосмислений за рахунок використання концептів (Concepts) та обмежень (Constraints), які були офіційно представлені у стандарті C++20 як одна з найважливіших його особливостей. Концепти дозволяють розробнику бібліотеки явно, декларативно специфікувати синтаксичні та семантичні вимоги до параметрів шаблону безпосередньо у його сигнатурі, створюючи строгий контракт між бібліотекою та користувачем.

Впровадження концептів у архітектуру Loki23 має декілька надзвичайно вагомих переваг, які виводять якість коду на новий рівень:
1. **Абсолютна самодокументованість коду**: Вимоги до політик тепер є формалізованою, невід'ємною частиною відкритого інтерфейсу класу. Будь-який розробник, дивлячись на оголошення шаблону, одразу чітко бачить, що саме вимагається від політики (наявність певних методів, визначених вкладених типів, конструкторів за замовчуванням чи копіювання). Це знімає необхідність у написанні кілометрових коментарів, які часто застарівають.
2. **Миттєве та раннє виявлення помилок**: Якщо переданий користувачем тип не задовольняє вказаний концепт, компілятор зупиняє роботу і видає коротке, точне та зрозуміле повідомлення про помилку (наприклад, "тип X не задовольняє концепту Y, оскільки не має методу Z") ще до того, як спробує інстанціювати складне тіло шаблону.
3. **Більш точне та елегантне перевантаження шаблонів**: Концепти можуть використовуватися для вибору найбільш підходящої спеціалізації шаблону залежно від властивостей типу, повністю замінюючи собою незграбні конструкції SFINAE. Компілятор тепер може алгоритмічно визначати, який концепт є більш специфічним (subsumption), обираючи найкращий варіант.
4. **Суттєве пришвидшення компіляції проектів**: Компілятору більше не потрібно марно витрачати ресурси та час на розгортання помилкових гілок шаблонів до самого кінця. Він просто відкидає типи, які не проходять перевірку концептом, на самому початку процесу парсингу.

Для наочного прикладу того, як це реалізовано, розглянемо модуль `loki23:hierarchy`. У ньому впроваджено концепт `Bindable`, який формально вимагає наявності шаблонного методу `bind` із заданою сигнатурою:

```cpp
template <typename T, typename E, typename... Args>
concept Bindable = requires(T t) {
  { t.template bind<Args...>(std::declval<Args>()...) } -> std::same_as<void>;
};
```

Цей концепт застосовує ключове слово `requires` для створення так званого requires-виразу. Всередині цього виразу компілятор намагається перевірити, чи є синтаксично коректним (well-formed) виклик шаблонного методу `bind` на фіктивному об'єкті `t` типу `T` з аргументами типу `Args...` (використовуючи `std::declval` для уникнення необхідності створення реальних об'єктів). Крім того, за допомогою стрілочного синтаксису `-> std::same_as<void>`, концепт жорстко перевіряє, чи повертає цей метод саме тип `void`, а не щось інше.

Такий строгий, формалізований підхід систематично та послідовно застосовано по всій кодовій базі бібліотеки Loki23. Під час ініціалізації будь-яких політик: політик створення (`CreationPolicy`), політик перевірки (`CheckingPolicy`) або політик володіння (`OwnershipPolicy`) явно вказуються очікувані властивості типів. Це повністю унеможливлює використання несумісних або частково реалізованих класів-політик на найбільш ранньому етапі компіляції та забезпечує монолітну, непробивну безпеку типів усієї бібліотеки.

## 4.2. Реалізація сучасного розумного вказівника (Loki23::SmartPtr) з повною підтримкою атомарних операцій та кастомних стратегій володіння

Класичний `Loki::SmartPtr` був неймовірно потужним, інноваційним та незамінним інструментом в епоху до появи стандартизованих та безпечних розумних вказівників, таких як `std::unique_ptr` та `std::shared_ptr`, які були додані лише у стандарті C++11. До того часу розробники мали у своєму арсеналі лише сумнозвісний та небезпечний `std::auto_ptr`, використання якого часто призводило до витоків пам'яті або невизначеної поведінки через його дивну семантику руйнівного копіювання. 

Однак, навіть сьогодні, у часи сучасного C++, незважаючи на величезну потужність, надійність та оптимізованість сучасних стандартних вказівників, вони все одно не завжди пропонують розробникам достатню гнучкість для вирішення специфічних та нестандартних архітектурних завдань. Стандартна бібліотека C++ пропонує універсальні рішення для 95% випадків, але для решти 5% складних систем потрібні спеціалізовані інструменти.

Наприклад, можна виділити наступні суттєві обмеження стандартних розумних вказівників:
* Популярний `std::shared_ptr` завжди і безумовно виділяє так званий контрольний блок (control block) для зберігання лічильника посилань на купі (heap). У системах реального часу, іграх, ядрах операційних систем або вбудованих системах з обмеженими ресурсами (embedded systems) часті алокації пам'яті на купі є категорично неприйнятними через фрагментацію та непередбачувані затримки.
* У стандартних вказівниках повністю відсутня можливість легко та декларативно змінити поведінку програми при перевірці вказівника перед розіменуванням. Наприклад, якщо програма намагається розіменувати нульовий `std::shared_ptr`, відбудеться жорстке падіння програми (Segmentation Fault). Розробник не може налаштувати вказівник так, щоб замість падіння він, наприклад, просто залогував помилку у файл, викинув спеціалізований C++ виняток (exception) та дозволив програмі продовжити роботу, або ініціював процедуру м'якого відновлення стану системи.
* Стандартні розумні вказівники розроблялися переважно для керування сирими вказівниками на пам'ять. Їх досить складно та незручно використовувати (через необхідність написання кастомних делітерів) для створення безпечних RAII-обгорток над системними ресурсами, що не є власне пам'яттю. Такими ресурсами можуть бути файлові дескриптори POSIX (цілі числа), мережеві сокети, хендли віконних підсистем Windows (HWND), дескриптори підключень до баз даних або об'єкти графічних API (OpenGL текстури, Vulkan буфери).
* Деякі існуючі у проектах класи та об'єкти (особливо у старих кодових базах або при інтеграції з C-бібліотеками чи COM-об'єктами) вже мають власні, вбудовані внутрішні механізми підрахунку посилань (наприклад, реалізують інтерфейс типу `IUnknown` з методами `AddRef` та `Release`). Це так звані інтрузивні об'єкти. Стандартний `std::shared_ptr` не вміє використовувати ці вбудовані лічильники безпосередньо і створюватиме свій власний, зовнішній лічильник, що призведе до дублювання даних, зайвих алокацій та розсинхронізації стану життєвого циклу.

Оновлений `Loki23::SmartPtr` блискуче розв'язує ці проблеми, повністю відновлюючи та примножуючи гнучкість оригінального Loki. Він пропонує узагальнений, високонастроюваний контейнер для управління будь-якими ресурсами, який гнучко конфігурується за допомогою незалежних політик. Фундаментальна реалізація `SmartPtr` розташована в модулі `loki23.smart_ptr`:

```cpp
template <typename Tval,
          typename OwnPolicy   = DeepCopy,
          typename CheckPolicy = NoCheck,
          template <typename> typename StorePolicy = DefaultStorage>
  requires (!std::same_as<OwnPolicy, IntrusiveOwnership> ||
            (IntrusiveCounted<Tval> &&
             std::same_as<typename StorePolicy<Tval>::handle_type, Tval *>))
class SmartPtr;
```

Наведений вище фрагмент коду ідеально демонструє неймовірну виразність та потужність концептів C++20. За допомогою ключового слова `requires` безпосередньо в оголошенні класу накладається складе логічне обмеження, яке діє як строгий охоронець архітектурної цілісності. Якщо користувач під час інстанціювання шаблону обирає специфічну політику володіння `IntrusiveOwnership` (яка передбачає, що об'єкт сам рахує посилання на себе), то компілятор негайно перевірить дві речі. По-перше, тип самого ресурсу `Tval` обов'язково повинен підтримувати інтрузивний підрахунок посилань (це перевіряється концептом `IntrusiveCounted<Tval>`). По-друге, внутрішній тип ручки (handle) обраної політики зберігання має бути саме звичайним сирим вказівником `Tval *`, а не чимось іншим (наприклад, не цілим числом). Якщо хоча б одна з цих умов не виконується, компіляція зупиниться з чітким поясненням причини. Це гарантує абсолютну логічну коректність архітектури ще до створення першого об'єкта класу.

### Детальний аналіз Політик перевірки (CheckingPolicy)
Політика перевірки є критичним елементом безпеки. Її головна мета — бути викликаною перед кожним доступом до інкапсульованого об'єкта (через перевантажені оператори розіменування `*` або доступу до членів `->`). Вона формалізується та закріплюється концептом `CheckingPolicy`:
```cpp
template <typename Policy>
concept CheckingPolicy = requires(bool b) {
  { Policy::check(b) } -> std::same_as<void>;
};
```
Як видно з концепту, політика повинна надавати статичний метод `check`, який приймає булеве значення (результат перевірки валідності ручки) і не повертає нічого (`void`). У Loki23 (модуль `loki23.smart_ptr.checking`) реалізовані та доступні "з коробки" такі готові варіанти поведінки:
* `NoCheck`: Оптимізована, екстремально швидка політика, що взагалі не робить ніяких перевірок. Її метод `check` порожній. Вона ідеально підходить для остаточних релізних збірок (Release builds), де продуктивність є критичною, і розробник математично впевнений у відсутності нульових вказівників у даному контексті. Забезпечує нульовий оверхед порівняно зі звичайним сирим вказівником.
* `AssertCheck`: Використовує стандартний макрос `assert` з бібліотеки `<cassert>`. Ця політика перевіряє валідність і зупиняє програму з детальним повідомленням про помилку лише в налагоджувальних збірках (Debug builds). У релізних збірках перевірка видаляється препроцесором, і політика перетворюється на аналог `NoCheck`.
* `ExceptionCheck`: Безпечний варіант для обробки помилок часу виконання. Якщо вказівник невалідний, політика динамічно викидає об'єкт винятку типу `std::runtime_error` з детальним повідомленням "SmartPtr: invalid handle". Це дозволяє викликаючому коду перехопити помилку в блоці `catch` і коректно обробити ситуацію без падіння всієї програми.
* `HaltCheck`: Найжорсткіша і найрадикальніша політика. Вона виводить червоне повідомлення про помилку безпосередньо у стандартний потік помилок `std::cerr` та негайно, без будь-яких спроб розгортання стеку (stack unwinding), викликає функцію `std::terminate()`. Використовується в системах, де продовження роботи з пошкодженим станом є небезпечнішим за миттєву зупинку.

### Розширений огляд Політик зберігання (StoragePolicy)
Ця політика є потужним рівнем абстракції, що відокремлює логіку володіння від фізичного способу зберігання "ручки" (handle) ресурсу. Вона дозволяє розумному вказівнику керувати абсолютно будь-якими ресурсами операційної системи, а не тільки динамічною пам'яттю. Концепт `StoragePolicy` вимагає наявності асоційованого внутрішнього типу `handle_type` (це може бути вказівник, ціле число, спеціальна структура) та реалізації базових методів для управління ним: `get()`, `set()`, `is_valid()` (чи вказує ручка на реальний ресурс), та `destroy()` (як саме звільняти ресурс).

У модулі `loki23.smart_ptr.storage` реалізовано такий багатий набір:
* `DefaultStorage` (також відомий через аліас `PointerStorage`): Класичний варіант. Зберігає звичайний `T*` і використовує стандартний оператор `delete` для його знищення.
* `LockedStorage`: Спеціалізована політика, що забезпечує потокобезпечний доступ до самого значення вказівника. Вона інкапсулює всередині себе `std::mutex` і загортає всі операції читання `get()` та запису `set()` у безпечні RAII-блоки `std::lock_guard<std::mutex>`. Це запобігає станам гонитви (race conditions), якщо кілька потоків намагаються одночасно змінити куди вказує один і той самий екземпляр `SmartPtr`.
* `FileDescriptorStorage`: Демонструє міць абстракції ручки. Зберігає звичайне ціле число типу `int` (стандартний хендл файлу в системах Unix/Linux). Знищення ресурсу в цій політиці полягає не у виклику `delete` (що було б помилкою), а у виклику системної POSIX-функції `::close(handle)`. Перевірка на валідність полягає в перевірці умови `handle >= 0`. Це перетворює `SmartPtr` на ідеальну RAII-обгортку для безпечної роботи з файлами, гарантуючи, що файл буде закрито при виході з області видимості, навіть якщо стався виняток.
* `SocketStorage`: Концептуально аналогічна до `FileDescriptorStorage`, але семантично призначена для надійного та автоматизованого керування мережевими сокетами, забезпечуючи їх коректне закриття та звільнення мережевих портів ОС.

### Комплексний аналіз Політик володіння (OwnershipPolicy)
Це найскладніша, найважливіша та найбільш функціонально насичена група політик (модуль `loki23.smart_ptr.ownership`). Вона визначає фундаментальну поведінку `SmartPtr` під час його копіювання, переміщення та знищення. Серед іншого, у бібліотеці доступні такі ретельно спроєктовані стратегії:
* `DeepCopy`: Забезпечує сувору семантику глибокого копіювання. При спробі скопіювати екземпляр розумного вказівника створюється абсолютно нова, повністю незалежна реальна копія об'єкта в пам'яті, на який він вказує. Ця політика вимагає, щоб інкапсульований об'єкт підтримував концепт `DeepCopyable` (мав поліморфний метод `deep_copy()`, що повертає новий вказівник) або хоча б мав доступний стандартний конструктор копіювання. Це ідеально для об'єктів-значень (value semantics), які мають бути повністю ізольовані.
* `RefCounted`: Забезпечує класичний підрахунок посилань (ідентично до філософії `std::shared_ptr`). Кілька вказівників можуть посилатися на один об'єкт. Ресурс буде знищено лише тоді, коли лічильник посилань впаде до абсолютного нуля. Лічильник динамічно виділяється на купі при першому створенні. Ця базова реалізація не є потокобезпечною і призначена для однопотокових оптимізованих сценаріїв.
* `RefCountedMT` (Multi-Threaded): Надійний, потокобезпечний підрахунок посилань. На відміну від попередньої політики, вона використовує атомарний лічильник `std::atomic<std::size_t>` замість звичайного цілого числа. Операції збільшення та зменшення лічильника використовують спеціалізовані бар'єри пам'яті (memory orders, такі як `memory_order_relaxed` для інкременту та `memory_order_acq_rel` для декременту), забезпечуючи максимальну продуктивність без ризику станів гонитви при багатопотоковому доступі до спільного об'єкта.
* `IntrusiveOwnership`: Елегантна стратегія, що делегує обов'язки з управління лічильником посилань та життєвим циклом безпосередньо самому об'єкту, на який вказує вказівник. Це вимагає, щоб об'єкт обов'язково підтримував специфічні методи, такі як `add_ref()` та `release()` (перевіряється концептом). Ця політика має нульовий оверхед по пам'яті, оскільки не потребує створення окремого зовнішнього контрольного блоку. Вона ідеальна для оптимізації ігрових движків, де кожен байт пам'яті має значення.
* `UniqueOwnership`: Сувора стратегія, яка на рівні компіляції категорично забороняє будь-які операції копіювання об'єкта вказівника. Вона дозволяє виключно семантику переміщення (move semantics), виступаючи концептуальним аналогом швидкого і безпечного `std::unique_ptr`. Гарантує, що в будь-який момент часу існує лише один-єдиний власник ресурсу.

Сучасна реалізація `Loki23::SmartPtr` повною, безкомпромісною мірою враховує новітні правила семантики переміщення (Move Semantics), яких концептуально не існувало і не могло існувати в оригінальному Loki C++98. Спеціальні конструктори переміщення та оператори присвоювання з переміщенням явно оголошені та імплементовані з використанням ключового слова `noexcept`. Це не просто синтаксична прикраса: це критично важлива підказка для компілятора та стандартних контейнерів, яка дозволяє, наприклад, `std::vector` радикально оптимізувати свою роботу. При реаллокації пам'яті вектора, замість повільного копіювання кожного розумного вказівника (з оновленням атомарних лічильників), вектор просто миттєво перемістить їх у нову ділянку пам'яті (через `memcpy` під капотом), оскільки розробник гарантував відсутність винятків під час цієї операції:

```cpp
SmartPtr(SmartPtr &&rhs) noexcept
    : storage_(std::move(rhs.storage_)), ownership_(std::move(rhs.ownership_)) {
  rhs.storage_.set(Store::null_handle()); // Переведення донора у безпечний порожній стан
}
```

Крім того, винахідливе використання концептів та обмежень (`requires` clauses) дозволяє неймовірно елегантно, прозоро та автоматично контролювати наявність та доступність операцій копіювання в інтерфейсі класу. Конструктор копіювання та оператор присвоювання з копіюванням у класі `SmartPtr` оголошені таким чином, що вони доступні для виклику користувачем лише і виключно у тому випадку, якщо обрана ним політика володіння (OwnershipPolicy) повністю задовольняє концепт `Clonable` (тобто логічно і фізично підтримує безпечну операцію клонування ресурсу). Це автоматично, без будь-яких додаткових зусиль розробника, робить вказівники типу "UniqueOwnership" суворо move-only типами (об'єктами, які можна лише переміщати). Розробнику більше не потрібно писати заплутані спеціалізації шаблонів або використовувати кілометри SFINAE-коду для вилучення методів копіювання з інтерфейсу класу.

## 4.3. Глибока модернізація паттерну Singleton: гарантована потокобезпека та складний контроль життєвого циклу об’єктів у C++23

Патерн Одинак (Singleton), вперше описаний "Бандою Чотирьох", є, мабуть, одним із найвідоміших, найпоширеніших, але водночас і найбільш жорстко критикованих патернів у спільноті C++. Багато авторитетних інженерів навіть відносять його до категорії "антипатернів" (anti-patterns) через те, що він приховує глобальний стан та ускладнює модульне тестування. Проте, у багатьох системних завданнях (керування логуванням, доступ до апаратних ресурсів системи, конфігурація додатка) він залишається об'єктивною необхідністю. Основними, фундаментальними проблемами класичних реалізацій цього патерну в C++ завжди були дві масштабні проблеми:

1. **Проблема складності забезпечення потокобезпеки**: Найпростіша, наївна реалізація відкладеної ініціалізації (lazy initialization, перевірка `if (instance == nullptr)`) є вкрай небезпечною і не є потокобезпечною у багатопотоковому середовищі: кілька потоків можуть одночасно побачити нульовий вказівник і створити кілька екземплярів "Одинака", викликаючи витоки пам'яті та руйнуючи логіку. Використання звичайного важкого об'єкта `std::mutex` при кожному, навіть мікросекундному доступі до екземпляра вбиває продуктивність системи нанівець, створюючи "вузьке горлечко" (bottleneck). Спроба обійти цю проблему продуктивності через винайдення патерну "Double-Checked Locking" (DCLP) у стандартах до C++11 була принципово помилковою та небезпечною. Оскільки мова не мала формалізованої моделі пам'яті (Memory Model), агресивний компілятор під час оптимізації або сучасний суперскалярний процесор під час виконання могли довільно переупорядковувати (reorder) машинні інструкції читання та запису пам'яті. Це часто призводило до жахливих наслідків: один потік міг побачити ненульовий вказівник на виділену пам'ять, але конструктор об'єкта ще не встиг завершити роботу в іншому потоці, що призводило до використання неповністю ініціалізованого "сміття" з пам'яті та краху програми.
2. **Проблема непередбачуваного порядку знищення статичних об'єктів (Static Initialization Order Fiasco та Dead Reference Problem)**: Міжнародний стандарт мови C++ не дає жодних гарантій щодо точного порядку ініціалізації та, що ще важливіше, руйнування глобальних і статичних об'єктів, які знаходяться у різних, незалежних одиницях трансляції (cpp-файлах). Якщо один складний синглтон (наприклад, система логування) критично залежить від іншого синглтона (наприклад, системи доступу до файлів) під час завершення програми, виникає величезна небезпека звернення до вже знищеного об'єкта (Dead Reference). Програма може успішно відпрацювати і раптово впасти під час свого завершення, що є вкрай неприємним багом.

Оригінальна бібліотека Loki пропонувала геніальні для свого часу, але надзвичайно складні, заплутані механізми відстеження тривалості життя та застосовувала ключове слово `volatile` у спробі зупинити оптимізації компілятора. Проте навіть це все одно не гарантувало 100% кросплатформної потокобезпеки у складних, сучасних багатоядерних та багатопроцесорних системах з послабленою моделлю пам'яті (наприклад, на архітектурі ARM).

У новій бібліотеці Loki23 клас `SingletonHolder` (розташований у модулі `loki23.singleton`) був повністю, з нуля модернізований з використанням жорстких гарантій сучасного стандарту (C++11/C++20). Зокрема, безпека досягається виключно через правильне використання атомарних типів `std::atomic` та глибоке розуміння суворих моделей доступу до пам'яті (Memory Models).

### Архітектура та конфігурація SingletonHolder
Гнучкість класу `SingletonHolder` досягається завдяки тому, що він налаштовується користувачем через дві незалежні стратегічні політики:
* `CreationPolicy` (Політика створення): Ця політика повністю відповідає за те, як об'єкт фізично створюється в пам'яті та як він потім знищується. Наприклад, політика `CreateUsingNew` є найпростішою і використовує стандартний глобальний оператор `new` (алокація на купі). Політика `CreateUsingMalloc` демонструє інтеграцію з C-стилем, використовуючи низькорівневі C-функції `std::malloc`/`std::free` та так званий placement new для виклику конструктора у виділеній пам'яті. Особливо цікавою є політика `CreateStatic`: вона гарантує, що об'єкт ніколи не буде виділятися на повільній купі. Замість цього вона використовує заздалегідь виділений масив статичної пам'яті правильного розміру та вирівнювання (`alignas(T) static std::byte storage[sizeof(T)]`) і конструює об'єкт прямо там. Це ідеально для вбудованих (embedded) систем.
* `LifetimePolicy` (Політика тривалості життя): Цей компонент бере на себе відповідальність керувати розкладом руйнування об'єкта під час завершення програми та визначати конкретну поведінку системи у критичному випадку виникнення проблеми "мертвого посилання" (звернення до синглтона після його смерті).

Сучасна реалізація доступу до єдиного екземпляра використовує високоефективний патерн Double-Checked Locking (DCLP), який тепер, завдяки можливостям C++, є математично та апаратно доведено безпечним. Це досягнуто завдяки використанню `std::atomic` та явній, ручній вказівці порядку доступу до пам'яті для уникнення будь-яких переупорядкувань:

```cpp
static T &instance() {
  T *p = pInstance_.load(std::memory_order_acquire);
  if (!p) {
    std::lock_guard lock{mutex_};
    p = pInstance_.load(std::memory_order_relaxed);
    if (!p) {
      if (destroyed_) {
        LifetimePol::on_dead_reference();
        destroyed_ = false;
      }
      p = CreationPol::create();
      pInstance_.store(p, std::memory_order_release);
      LifetimePol::schedule_destruction(p, &destroy_singleton);
    }
  }
  return *p;
}
```

Детальний покроковий механізм роботи цього надважливого алгоритму є наступним:
1. **Перша швидка перевірка** (виконується поза повільним м'ютексом) використовує атомарне завантаження `std::memory_order_acquire`. Це встановлює так звану гарантію "Acquire" (набуття). Вона створює жорсткий односторонній бар'єр пам'яті, який суворо забороняє як процесору, так і компілятору переносити будь-які інструкції читання пам'яті, що знаходяться в коді після цієї перевірки, вище цього виклику. Тому, якщо наш потік побачить ненульовий вказівник `p`, ми математично гарантовано бачимо і повністю ініціалізований об'єкт у пам'яті, без жодного ризику натрапити на частково сконструйований стан.
2. Якщо вказівник виявився нульовим (тобто об'єкт ще не створено), потік змушений захопити глобальне блокування (`std::lock_guard lock{mutex_}`). Це дуже "дорога" та повільна системна операція, яка перемикає контекст потоків, але найважливіше те, що вона відбувається лише і виключно під час найпершого звернення до синглтона за весь час роботи програми.
3. **Друга перевірка** (яка відбувається вже всередині захищеної критичної секції) використовує значно простіший `std::memory_order_relaxed`. Тут суворі бар'єри пам'яті більше не потрібні. Чому? Тому що сам об'єкт м'ютекса (`std::mutex`) згідно зі стандартом C++ вже діє як абсолютний повний бар'єр пам'яті (Full Memory Barrier) при його захопленні (lock) та звільненні (unlock).
4. Після успішного створення об'єкта через обрану політику `CreationPol::create()`, новий валідний вказівник записується назад у статичну змінну за допомогою `std::memory_order_release`. Це встановлює гарантію "Release" (вивільнення). Вона змушує кеші процесора синхронізуватися і гарантує, що всі записи в пам'ять (тобто всі поля новоствореного та ініціалізованого об'єкта) стануть стовідсотково видимими для всіх інших ядер процесора до того, як туди буде публічно записаний власне сам вказівник `pInstance_`.

### Управління життєвим циклом (LifetimePolicy) у деталях
Для вирішення проблеми порядку руйнування додатково реалізовано внутрішній механізм відстеження "мертвих посилань". Спеціальна статична змінна `destroyed_` фіксує факт успішного руйнування синглтона на етапі завершення роботи програми (виклик деструктора відбувається всередині функції `destroy_singleton`, яка реєструється операційною системою через системний виклик `std::atexit`).

У модулі `loki23.singleton.lifetime` реалізовані глибоко продумані політики, що визначають, як програма повинна реагувати на небезпечне звернення до вже мертвого об'єкта:
* `DefaultLifetime`: Найпростіший і найбезпечніший варіант. При спробі доступу до мертвого синглтона політика просто генерує критичний виняток `std::logic_error{"Dead Reference Detected"}`, сигналізуючи розробнику про серйозну архітектурну помилку в порядку залежностей модулів системи.
* `PhoenixSingleton` (Синглтон Фенікс): Елегантне та магічне розв'язання проблеми. Якщо до синглтона (наприклад, системи логування, якій потрібно записати інформацію про завершення роботи) знову звертаються інші об'єкти після того, як він був офіційно знищений системою, ця політика ігнорує мертвий стан (встановлюючи `destroyed_once_ = true`). Вона дозволяє синглтону буквально "відродитися з попелу" подібно до міфічного птаха Фенікса — `SingletonHolder` просто пройде процедуру ініціалізації ще раз і створить об'єкт наново, а потім знову коректно його знищить в самому кінці.
* `SingletonWithLongevity`: Найбільш складний, гнучкий та інноваційний варіант контролю. Він дозволяє архітектору вручну призначити кожному синглтону в системі специфічний числовий пріоритет — показник "довговічності" (Longevity). Під час ініціалізації та знищення програма використовує прихований глобальний масив `tracker_array`, що містить поліморфні об'єкти типу `LifetimeTracker`. Ці трекери автоматично сортуються в масиві за показником їх довговічності. Таким чином, гарантується, що синглтони з меншою довговічністю завжди і безумовно знищуються раніше за ті синглтони, що мають більшу довговічність. Це дозволяє архітектору жорстко та детерміновано задати ієрархію руйнування і повністю і назавжди вирішити проблему циклічних залежностей між глобальними об'єктами.

## 4.4. Реалізація потужних ієрархій класів на основі списків типів

Генерація ієрархій класів — це унікальний, високорівневий метапрограмний механізм, що дозволяє бібліотеці автоматично, програмно створювати складні, розгалужені або лінійні структури спадкування класів на основі простого списку переданих типів прямо на етапі компіляції. Це ідеально підходить і часто є життєво необхідним для створення узагальнених реалізацій таких складних патернів, як Abstract Factory (Абстрактна Фабрика) або Visitor (Відвідувач), де точна кількість та конкретні типи сутностей у системі можуть постійно змінюватися під час розвитку проекту.

В оригінальному, класичному Loki списки типів (знаменитий клас `TypeList`) реалізовувалися як примітивні рекурсивні структури-вузли (подібно до пар Head/Tail у функціональних мовах програмування на зразок LISP). Маніпуляції з ними вимагали написання величезної кількості допоміжного шаблонного коду для їх обходу, зшивання та пошуку. У Loki23 використання новітніх варіативних шаблонів (variadic templates) дозволило назавжди відмовитися від цих застарілих конструкцій, замінивши їх на значно простіший, зрозуміліший та ефективніший для компілятора контейнер `template <typename... Ts> struct type_list`.

Бібліотека майстерно реалізує два принципово різних типи ієрархій у модулі `loki23:hierarchy`: розсіяну (`GenScatterHierarchy`) та лінійну (`GenLinearHierarchy`). Кожна з них вирішує свій клас архітектурних завдань.

### 4.4.1. Розсіяна ієрархія (GenScatterHierarchy)
Розсіяна ієрархія базується на парадигмі множинного спадкування. Вона приймає як параметри базовий шаблон одиниці обробки (клас `Unit`, який інкапсулює логіку для одного конкретного типу) і варіативний список цільових типів `Ts...`. Підсумковий згенерований клас паралельно і безпосередньо спадкує всі необхідні інстанціації базового шаблону-одиниці для кожного типу, що входив до списку:

```cpp
template <template <class> class Unit, typename... Ts>
struct GenScatterHierarchy<Unit, type_list<Ts...>>
    : public GenScatterHierarchy<Unit, Ts>... {};
```

Цей невеликий, але неймовірно потужний фрагмент коду використовує синтаксис розпакування пакета параметрів (`...`) безпосередньо у списку специфікаторів базових класів (base class list). Це, без перебільшення, одна з найпотужніших та найвиразніших можливостей сучасного C++. Замість вибудовування довгого, глибокого і незграбного ланцюжка рекурсивних успадкувань `Left/Right` (як це вимушено робилося в C++98), новий клас просто паралельно, плоским списком успадковує всі необхідні базові класи. 

Це рішення має колосальні переваги. Воно не лише радикально спрощує читабельність коду (роблячи його тривіальним), а й, що набагато важливіше, дозволяє сучасним компіляторам застосовувати критичну оптимізацію порожнього базового класу (EBCO - Empty Base Class Optimization) значно ефективніше. В результаті, складна ієрархія, що містить десятки політик-обробників, у пам'яті під час виконання програми може займати рівно нуль додаткових байтів, зберігаючи при цьому всю повноту поліморфного інтерфейсу.

Доступ до потрібного підкомпонента (конкретного базового класу для заданого типу `T`) всередині такої розсіяної ієрархії зручно здійснюється за допомогою вільної глобальної допоміжної функції `Field`:

```cpp
template <typename T, template <class> class Unit, typename AnyList>
Unit<T> &Field(GenScatterHierarchy<Unit, AnyList> &obj) {
  return static_cast<Unit<T> &>(obj);
}
```
Використовуючи безпечний `static_cast` на етапі компіляції, ми алгоритмічно піднімаємося по плоскій ієрархії множинного спадкування до потрібного нам інтерфейсу `Unit<T>`, не витрачаючи жодного такту процесорного часу під час виконання програми.

### 4.4.2. Лінійна ієрархія (GenLinearHierarchy)
На відміну від розсіяної, лінійна ієрархія будує суворий, послідовний вертикальний ланцюжок спадкування: обробник для типу `T1` публічно спадкує обробник для типу `T2`, який, у свою чергу, спадкує обробник для `T3`, і так далі до кінця списку. Ця архітектурна топологія є критично корисною та необхідною для імплементації патерну "Ланцюжок відповідальностей" (Chain of Responsibility), складних обробників подій (event handlers) або систем диспетчеризації, де строгий порядок перевірки чи обробки має фундаментальне значення для бізнес-логіки.

Оскільки мова C++ семантично не підтримує розпакування пакета параметрів у вертикальний ланцюжок спадкування безпосередньо одним тривіальним виразом, реалізація змушена використовувати класичний патерн рекурсії хвостового типу на рівні метапрограмування з використанням часткової спеціалізації шаблонів структури `type_list`:

```cpp
template <template <class> class Unit, typename T, typename... Ts>
struct GenLinearHierarchy<Unit, type_list<T, Ts...>>
    : public GenLinearHierarchy<Unit, T>,
      GenLinearHierarchy<Unit, type_list<Ts...>> {};
```

Незважаючи на використання рекурсії, така лінійна ієрархія забезпечує архітектору стовідсотково точний, детермінований контроль над фізичним розташуванням даних у пам'яті фінального об'єкта та, що найголовніше, над строгим, гарантованим порядком виклику конструкторів (від базових до похідних) і деструкторів (у зворотному порядку). Це є абсолютно критичною вимогою для систем із жорсткими архітектурними обмеженнями, де порушення порядку ініціалізації призводить до краху.

## 4.5. Інноваційні мультиметоди (Multiple Dispatch) у Modern C++

Класичний, вбудований у мову механізм віртуальних функцій C++ за своєю природою забезпечує виключно одинарну диспетчеризацію (Single Dispatch). Це означає, що поліморфна поведінка програми динамічно залежить лише від фактичного типу одного-єдиного об'єкта — того самого, через який безпосередньо здійснюється виклик методу (це прихований аргумент `this`). 

Однак, у величезній кількості реальних, складних системних завдань виникає об'єктивна необхідність виконувати специфічну логіку на основі одночасного аналізу динамічних типів одразу *двох* або навіть більше незалежних об'єктів. Найяскравішими прикладами є:
* **Фізичні рушії та відеоігри**: При розрахунку зіткнень складної геометрії (Collision Detection), алгоритм реакції об'єкта "Астероїд" при зіткненні з об'єктом "Космічний корабель гравця" має бути зовсім інакшим і використовувати іншу математику, ніж при зіткненні об'єкта "Плазмовий лазер" з тим самим "Космічним кораблем".
* **Компілятори та аналізатори коду**: Під час виконання складних семантичних операцій або оптимізацій над вузлами абстрактних синтаксичних дерев (AST).

Ця архітектурна дилема відома в комп'ютерних науках як проблема множинної диспетчеризації (Multiple Dispatch). Традиційно, у підручниках з об'єктно-орієнтованого проектування, для її вирішення пропонується використовувати громіздкий патерн Visitor (Відвідувач). Проте досвід індустрії показує, що класичний Відвідувач є дуже "токсичним" патерном: він створює жорсткі, нерозривні циклічні залежності між усіма класами ієрархії і вимагає постійної, болючої модифікації центрального базового інтерфейсу (що порушує принцип відкритості-закритості, Open-Closed Principle) при додаванні будь-яких нових підтипів у систему, що робить його непридатним для бібліотек, що розширюються.

Бібліотека Loki23 (в рамках модуля `loki23:multimethods`) пропонує комплексне, узагальнене розв'язання цієї вічної проблеми, надаючи архітекторам два потужних, взаємодоповнюючих інструменти: статичний диспетчер (`StaticDispatcher`) для закритих систем та динамічний диспетчер (`DynamicDispatcher`) для відкритих плагінних архітектур.

### Глибинний аналіз Статичного диспетчера (StaticDispatcher)
Цей тип диспетчера використовується переважно тоді, коли архітектура системи є "закритою", тобто всі можливі цільові типи в ієрархії гарантовано відомі розробнику на етапі компіляції програми. Головна перевага `StaticDispatcher` полягає в тому, що він не вимагає абсолютно жодних змін у базових або похідних класах (не потрібно додавати методи `accept`). Він повністю базується на генерації оптимізованих, каскадних серій перевірок типів через безпечний оператор `dynamic_cast`.

Використання інноваційних виразів згортки (fold expressions), представлених у C++17, дозволило авторам Loki23 замінити старі, надзвичайно громіздкі рекурсивні алгоритми генерації коду на дуже компактний, елегантний і максимально ефективний для компілятора алгоритм:

```cpp
template <typename BaseLhs, typename BaseRhs, typename ExecutorType, typename... Ts>
struct StaticDispatcherExecutor<DispatchPolicy::FIRST_MATCH, BaseLhs, BaseRhs, ExecutorType, Ts...> {
  template <typename... Functors> static int execute(BaseLhs *lhs, BaseRhs *rhs, Functors... execs) {
    return (... || ([&]() {
              if (auto *l = dynamic_cast<Ts *>(lhs)) {
                return (... || ([&]() {
                          if (auto *r = dynamic_cast<Ts *>(rhs)) {
                            Executor<DispatchPolicy::FIRST_MATCH, ExecutorType>::execute(l, r, execs...);
                            return 1;
                          }
                          return 0;
                        }()));
              }
              return false;
            }()));
  }
};
```
Цей на перший погляд складний шаблонний код насправді генерує та розгортає повну двовимірну матрицю перевірок типів.
1. У зовнішньому циклі шаблонної згортки `(... || ...)` система ітерується по всіх можливих підтипах лівого аргументу (об'єкта `lhs`). Як тільки перевірка `dynamic_cast<Ts *>(lhs)` завершується успішно (повертає ненульовий вказівник), виконання негайно переходить у внутрішню лямбда-функцію.
2. У внутрішній згортці `(... || ...)` алгоритм аналогічно перевіряє правий поліморфний аргумент `rhs` на відповідність типам з масиву типів `Ts`. 
3. Оскільки в даній спеціалізації використовується логічне АБО (`DispatchPolicy::FIRST_MATCH`), компільований машинний код розгортається у плоску, високооптимізовану лінійну послідовність низькорівневих `if-else` інструкцій (з так званим коротким замиканням, short-circuit evaluation). Це гарантує, що виконання миттєво зупиняється на першому ж вдалому збігу типів, мінімізуючи витрати процесорного часу на непотрібні касти.

Для більш складних випадків, коли архітектурі потрібно обробити *всі можливі* збіги типів (наприклад, якщо об'єкти системи використовують складне множинне спадкування і одночасно реалізують кілька різних інтерфейсів), у бібліотеці реалізовано спеціалізацію з політикою `DispatchPolicy::ALL_MATCHES`. У цій гілці замість логічного АБО використовується арифметичне додавання `(... + ...)`. Це хитре рішення змушує компілятор згенерувати код, який обійде і перевірить абсолютно всі гілки графа спадкування, накопичуючи кількість успішних викликів обробників.

### Архітектура Динамічного диспетчера (DynamicDispatcher)
У сучасних додатках система часто є архітектурно відкритою. Ієрархія типів може розширюватися плагінами або модулями (DLL/SO) прямо в процесі виконання програми, або типи можуть бути фізично розбиті по різних динамічних бібліотеках, які нічого не знають одна про одну на етапі компіляції. У таких умовах статична генерація матриці `dynamic_cast` є неможливою. Саме тут застосовується `DynamicDispatcher`. Замість генерації масивного і жорсткого блоку коду на етапі компіляції, процес реєстрації функцій-обробників відбувається гнучко у процесі виконання (в runtime).

Надійним технічним фундаментом `DynamicDispatcher` у Loki23 є використання стандартизованих інструментів ідентифікації типів часу виконання (RTTI). Бібліотека використовує клас `std::type_index` (який є легкою обгорткою над `type_info`) для унікальної ідентифікації типів, та застосовує високоефективну хеш-таблицю стандартної бібліотеки `std::unordered_map` для зберігання зареєстрованих користувачем функцій зворотного виклику (callbacks, упакованих у поліморфні обгортки `std::function`).

```cpp
template <DispatchPolicy dispatch_policy, typename NoMatchPolicy, typename... Args> 
struct DynamicDispatcher {
  static constexpr std::size_t n_args{sizeof...(Args)};
  using Callback = std::function<void(Args...)>;

  std::conditional_t<dispatch_policy == DispatchPolicy::FIRST_MATCH,
                     std::unordered_map<std::array<std::type_index, n_args>, Callback, TypeIndexArrayHash>,
                     std::unordered_multimap<std::array<std::type_index, n_args>, Callback, TypeIndexArrayHash>>
      callbacks_;
  // ... методи для реєстрації та диспетчеризації
};
```

Ключем для доступу до цієї хеш-таблиці виступає не один тип, а композитний масив індексів типів `std::array<std::type_index, n_args>`. Щоб ця мапа працювала з максимально можливою ефективністю і не ставала вузьким місцем у системі, авторам бібліотеки довелося розробити власний, спеціалізований та математично вивірений хешер `TypeIndexArrayHash`. Цей хешер ефективно комбінує (мікшує) хеш-коди від кожного окремого `std::type_index` у масиві за допомогою операції побітового виключного АБО (`^`) у поєднанні з циклічним зсувом бітів вліво (shift left):

```cpp
struct TypeIndexArrayHash {
  template <std::size_t size> std::size_t operator()(std::array<std::type_index, size> array) const {
    static std::size_t hash{}; // Оптимізація кешування
    if (size == 0) return hash;
    
    hash = array[0].hash_code(); // Ініціалізація бази
    for (std::size_t i{}; i != size; ++i) {
      // Магічна константа і зсув для рівномірного розподілу бітів хешу
      hash ^= array[i].hash_code() << i; 
    }
    return hash;
  }
};
```

Цей інженерний підхід до алгоритму хешування забезпечує максимально рівномірний розподіл ключів у внутрішніх корзинах (buckets) таблиці `std::unordered_map`. Як наслідок, він гарантує надзвичайно швидкий пошук і вибір потрібного обробника подій з константною асимптотичною складністю $O(1)$ незалежно від кількості зареєстрованих політик. Це робить `DynamicDispatcher` досконалим і незамінним архітектурним інструментом для створення складних, масштабованих систем, що вимагають екстремально високої розширюваності та здатності швидко та детерміновано реагувати на складні події (повідомлення), які залежать від багатьох типів одночасно (мульти-сигнатури).
