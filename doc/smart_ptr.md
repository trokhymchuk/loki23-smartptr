# Розумний покажчик на основі політик: архітектура та параметризація

## Загальна структура

Клас `SmartPtr` реалізований як шаблонний тип із чотирма параметрами:

```cpp
template <typename Tval,
          typename OwnPolicy   = DeepCopy,
          typename CheckPolicy = NoCheck,
          template <typename> typename StorePolicy = DefaultStorage,
          typename ConvPolicy  = DisallowConversion>
  requires ((!std::same_as<OwnPolicy, IntrusiveOwnership> ||
             (IntrusiveCounted<Tval> &&
              std::same_as<typename StorePolicy<Tval>::handle_type, Tval *>)) &&
            ConversionPolicy<ConvPolicy, typename StorePolicy<Tval>::handle_type>)
class SmartPtr;
```

Перший параметр — `Tval` — тип керованого об'єкта і не є політикою. Решта три параметри задають незалежні *політики* — стратегії поведінки, що підмінюються без зміни основного коду класу. Такий підхід, запропонований Андрієм Александреску в бібліотеці Loki, забезпечує комбінаторну гнучкість: розробник конфігурує поведінку покажчика у місці оголошення типу, а не через успадкування чи умовну компіляцію.

Бібліотека визначає чотири осі конфігурації:

* **`OwnPolicy`** — стратегія копіювання та підрахунку посилань: хто є власником ресурсу та що відбувається при копіюванні покажчика. Приклади: `RefCounted` (спільна власність через лічильник), `NoCopy` (лише переміщення).
* **`CheckPolicy`** — реакція на звернення через недійсний (нульовий) дескриптор. Приклади: `NoCheck` (без перевірки, типово), `ExceptionCheck` (кидає `std::runtime_error`).
* **`StorePolicy`** — тип дескриптора та спосіб звільнення ресурсу: вказівник, файловий дескриптор, сокет тощо. Приклади: `DefaultStorage<T>` (звичайний `T*`, звільнення через `delete`), `FileDescriptorStorage<T>` (POSIX `int`, закриття через `::close`).
* **`ConvPolicy`** — дозвіл або заборона неявного перетворення `SmartPtr` до сирого дескриптора. Приклади: `DisallowConversion` (типово, перетворення відсутнє), `AllowConversion` (активує `operator handle_type()`).

## 1. Політика володіння (`OwnPolicy`)

Визначає семантику копіювання та підрахунку посилань — тобто відповідає на питання «хто і як відповідає за ресурс».

Будь-яка коректна політика повинна задовольняти концепт `OwnershipPolicy`:

```cpp
template <typename Policy, typename Thandle>
concept OwnershipPolicy = requires(Policy policy, Thandle h) {
    { policy.acquire(h) } -> std::same_as<void>;
    { policy.release(h) } -> std::same_as<bool>;
};
```

Та концепт `Clonable` — якщо підтримується копіювання:

```cpp
template <typename Policy, typename Thandle>
concept Clonable = requires(Policy policy, Thandle h) {
    { policy.clone(h) } -> std::same_as<Thandle>;
};
```

### Доступні значення

#### `DeepCopy` *(типове значення)*

Під час копіювання `SmartPtr` виклик `clone()` створює нову копію об'єкта в купі. Якщо тип `Tval` реалізує метод `deep_copy()`, він викликається напряму; інакше використовується конструктор копіювання (`new Tval{*v}`). Кожен екземпляр `SmartPtr` є єдиним власником свого ресурсу, тому при знищенні виконується `delete`. Схема відповідає семантиці `std::unique_ptr` із явним клонуванням.

**Застосування:** об'єкти, що не можуть ділитися станом; ієрархії із віртуальним `deep_copy()`.

---

#### `NoCopy`

Метод `clone()` видалений (`= delete`). Клас `SmartPtr` стає некопійованим — дозволений лише переміщення. Це найстрогіша форма ексклюзивного володіння, аналог `std::unique_ptr` без можливості клонування.

**Застосування:** ресурси, передача яких у спільне використання семантично некоректна (наприклад, дескриптор пристрою).

---

#### `Copy`

Поверхнева копія: `clone()` повертає той самий покажчик без жодного лічильника. Кожен екземпляр викликає `destroy()` при знищенні незалежно від інших, що призводить до подвійного звільнення при наявності двох і більше власників. Цей режим призначений для ситуацій, де час життя об'єктів гарантовано узгоджений ззовні.

**Застосування:** некерований код із зовнішньо гарантованим часом життя.

---

#### `RefCounted`

Реалізує спільне (shared) володіння через лічильник посилань, розміщений у купі (`std::size_t*`). `acquire()` виділяє лічильник і ініціалізує його значенням 1; `clone()` збільшує лічильник; `release()` зменшує — і повертає `true` (сигнал до звільнення ресурсу) лише при досягненні нуля. Лічильник не захищений від одночасного доступу з кількох потоків.

**Застосування:** однопотокові програми зі спільним користуванням об'єктів — аналог `std::shared_ptr` без накладних витрат на атомарність.

---

#### `RefCountedMT`

Потокобезпечний варіант `RefCounted`. Лічильник посилань має тип `std::atomic<std::size_t>*`. Збільшення відбувається з порядком `memory_order_relaxed`, зменшення — з `memory_order_acq_rel`, що гарантує коректну видимість операцій звільнення між потоками без надмірних бар'єрів пам'яті.

**Застосування:** багатопотокові програми, де `SmartPtr` може копіюватися з різних потоків одночасно.

---

#### `RefLinked`

Альтернативна схема підрахунку посилань без окремо виділеного лічильника. Кожен екземпляр `SmartPtr` зберігає власний вузол у спільному двозв'язному списку (`std::list<RefLinked*>`). При копіюванні вузол додається до списку, при знищенні — видаляється; ресурс звільняється тоді, коли список стає порожнім. Метод `use_count()` повертає поточний розмір списку.

**Застосування:** сценарії, де виділення пам'яті для окремого лічильника є небажаним; навчальні або дослідницькі реалізації.

---

#### `UniqueOwnership`

Конструктор копіювання та оператор копіювального присвоєння видалені. Переміщення дозволено. `release()` завжди повертає `true`. Семантично еквівалентний `NoCopy`, але сформульований як окрема концепція *ресурсного* (а не копіювального) контролю — призначений для використання разом із нестандартними сховищами.

**Застосування:** файлові дескриптори, сокети, будь-які некопійовані системні ресурси.

---

#### `SharedOwnership`

Потокобезпечна спільна власність без атомарного лічильника — успадковує `RefCountBase` (лічильник `std::size_t*`). Семантично еквівалентна `RefCounted`, але є окремою концепцією для ресурсних сховищ (не передбачає `clone()` через успадкований API). Дозволяє як копіювання, так і переміщення самої структури лічильника.

**Застосування:** спільне управління POSIX-ресурсами в межах одного потоку.

---

#### `IntrusiveOwnership`

Делегує підрахунок посилань безпосередньо об'єкту. Тип `Tval` повинен задовольняти концепт `IntrusiveCounted`:

```cpp
template <typename T>
concept IntrusiveCounted = requires(T &t) {
    t.add_ref();
    { t.release()   } -> std::convertible_to<int>;
    { t.ref_count() } -> std::convertible_to<int>;
};
```

`acquire()` та `clone()` викликають `h->add_ref()`; `release()` викликає `h->release()` і повертає `true` при результаті 0. Лічильник зберігається всередині об'єкта, що позбавляє від окремого динамічного виділення.

**Застосування:** COM-об'єкти, об'єкти з вбудованим `intrusive_ptr`-сумісним лічильником.

## 2. Політика перевірки (`CheckPolicy`)

Визначає реакцію на спробу доступу через недійсний (нульовий) дескриптор. Концепт:

```cpp
template <typename Policy>
concept CheckingPolicy = requires(bool b) {
    { Policy::check(b) } -> std::same_as<void>;
};
```

Метод `check()` є статичним і приймає булеве значення результату `Store::is_valid()`.

### Доступні значення

#### `NoCheck` *(типове значення)*

Перевірка відсутня: `check()` — порожня функція. Звернення через недійсний покажчик призводить до невизначеної поведінки. Оптимальне рішення для release-збірок із гарантованою коректністю вхідних даних.

---

#### `AssertCheck`

Викликає `assert(valid)` із діагностичним повідомленням. Перевірка активна лише у debug-збірках (де `NDEBUG` не визначено) і усувається компілятором у release-режимі.

---

#### `ExceptionCheck`

Кидає `std::runtime_error` при недійсному дескрипторі. Придатне для бібліотечного коду, де аварійне завершення процесу неприпустиме, а помилку можна обробити на вищому рівні.

---

#### `HaltCheck`

Виводить діагностику у `std::cerr` і негайно зупиняє програму через `std::terminate()`. Відрізняється від `AssertCheck` тим, що завжди активне (не залежить від `NDEBUG`) та не дозволяє перехопити помилку.

---

## 3. Політика зберігання (`StorePolicy`)

Шаблонний параметр виду `template <typename> typename` — задає тип дескриптора та стратегію звільнення ресурсу. Концепт:

```cpp
template <typename Policy>
concept StoragePolicy = requires(Policy p, typename Policy::handle_type h) {
    typename Policy::handle_type;
    { p.get()            } -> std::same_as<typename Policy::handle_type>;
    { p.set(h)           } -> std::same_as<void>;
    { Policy::null_handle() } -> std::same_as<typename Policy::handle_type>;
    { Policy::is_valid(h) }  -> std::same_as<bool>;
    { Policy::destroy(h) }   -> std::same_as<void>;
};
```

### Доступні значення

#### `DefaultStorage<T>` *(типове значення)*

`handle_type` — `T*`. Нульовий дескриптор — `nullptr`. Звільнення — `delete h`. Найпростіша і найпоширеніша схема зберігання для об'єктів у купі.

---

#### `PointerStorage<T>`

Семантичний псевдонім для `DefaultStorage<T>`. Реалізовано через `using PointerStorage = DefaultStorage`. Дозволяє виразити намір у типі без зміни поведінки.

---

#### `LockedStorage<T>`

`handle_type` — `T*`. Методи `get()` і `set()` захищені `std::mutex` через `std::lock_guard`. Забезпечує атомарність читання та запису покажчика з різних потоків. Звільнення — `delete h` (не захищено м'ютексом, оскільки виконується при знищенні об'єкта, коли інші посилання вже відсутні).

**Застосування:** `SmartPtr`, дескриптор якого може оновлюватися з різних потоків (наприклад, при атомарній заміні ресурсу).

---

#### `FileDescriptorStorage<T>`

`handle_type` — `int`. Нульовий (недійсний) дескриптор — `-1`. Звільнення — `::close(h)`. Дозволяє використовувати `SmartPtr` для управління часом життя POSIX-файлових дескрипторів із тією ж семантикою, що й для покажчиків. Параметр `T` є фантомним типом, що задовольняє сигнатуру шаблону `StorePolicy`.

---

#### `SocketStorage<T>`

`handle_type` — `int`. Нульовий дескриптор — `-1`. Звільнення — `::close(h)`. Структурно ідентична `FileDescriptorStorage`, але семантично виражає управління мережевими сокетами. Розмежування на рівні типів дозволяє застосовувати різні перевантаження або спеціалізації в залежності від призначення дескриптора.

---

## 4. Політика перетворення (`ConvPolicy`)

Визначає, чи надає `SmartPtr` неявне перетворення до сирого дескриптора. Концепт:

```cpp
template <typename Policy, typename Tptr>
concept ConversionPolicy = requires {
    { Policy::implicit_convert() } -> std::same_as<bool>;
};
```

Якщо `implicit_convert()` повертає `true`, клас надає `operator handle_type()`, захищений `CheckPolicy::check()`. Якщо `false` — оператор відсутній (обмеження через `requires` на рівні методу), і будь-яке неявне перетворення є помилкою компіляції.

### Доступні значення

#### `DisallowConversion` *(типове значення)*

Неявне перетворення заборонено. Єдиний спосіб отримати дескриптор — явний виклик `get()`. Захищає від випадкового передавання `SmartPtr` туди, де очікується сирий покажчик, і усуває цілий клас помилок із двічі-звільненою пам'яттю.

---

#### `AllowConversion`

Активує `operator handle_type() const`, що дозволяє неявно використовувати `SmartPtr` у контекстах, де очікується `handle_type`. Зручне для поступової міграції коду з сирих покажчиків або при взаємодії з C API, що приймають покажчик напряму.

---

## Зведена таблиця параметрів

| Параметр       | Типове значення       | Альтернативні значення |
|----------------|-----------------------|------------------------|
| `OwnPolicy`    | `DeepCopy`            | `NoCopy`, `Copy`, `RefCounted`, `RefCountedMT`, `RefLinked`, `UniqueOwnership`, `SharedOwnership`, `IntrusiveOwnership` |
| `CheckPolicy`  | `NoCheck`             | `AssertCheck`, `ExceptionCheck`, `HaltCheck` |
| `StorePolicy`  | `DefaultStorage<T>`   | `PointerStorage<T>`, `LockedStorage<T>`, `FileDescriptorStorage<T>`, `SocketStorage<T>` |
| `ConvPolicy`   | `DisallowConversion`  | `AllowConversion` |

---

## Обмеження при комбінуванні

Клас накладає два статичні обмеження через `requires`-вираз:

* якщо `OwnPolicy = IntrusiveOwnership`, то `Tval` повинен задовольняти концепт `IntrusiveCounted`, а `StorePolicy` повинна мати `handle_type = Tval*`;
* `ConvPolicy` повинна задовольняти концепт `ConversionPolicy` — тобто надавати статичний метод `implicit_convert() -> bool`.

Решта поєднань є коректними за визначенням концептів — компілятор відхилить недопустимі конфігурації на етапі інстанціювання шаблону.
